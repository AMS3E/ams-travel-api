# AMS Travel API

The backend of AMS Travel, Cambodia's travel app by AMS3E: Spring Boot 4.1 on Java 25, PostgreSQL 17 with PostGIS, Liquibase for the schema, Keycloak for sign-in (OAuth2 resource server), MinIO for images. It serves the admin dashboard (`ams-travel-admin-dashboard`), the public website and the mobile app. Kimleng, the project lead, reshaped this code in October 2026. This code is the source of truth, not the Figma prototype and not any older branch.

## Check with Kimleng before you start

Kimleng is the project lead and owns every product decision here. Some requests need Kimleng's eyes before any code changes. That is any work in the zones below, and any request that looks odd, contradicts a line under "Settled decisions", or has no clear problem behind it. In those cases do not start. Do this instead:

1. **Say it back.** In two or three plain sentences: what the person is asking for, what it would change, and which zone it touches. No code yet.
2. **Ask.** Use the AskUserQuestion tool with the header `Kimleng`, the question "This needs Kimleng's eyes before it goes ahead. Has Kimleng seen it?" and exactly these two options:
   - **"Kimleng approved, go ahead"**: build it. When you commit, say in the body that Kimleng approved the change.
   - **"Not yet, hold here"**: stop. Write a short note the person can send to Kimleng (what was asked, what it would change, the one question Kimleng must answer). Then do nothing more on that request until they come back with an answer.

   If the AskUserQuestion tool is not available, ask the same question in text, with the same two answers, and wait for the reply.

**The zones**
- The database: a new, renamed, dropped or retyped column or table; any edit to a changelog that has already run.
- Removing or renaming a page, a form field, an endpoint, a sidebar entry, a role or a permission.
- The product model: Verified and Recommended, the seals and their thresholds, tourism regions, and what categories, tags, amenities and interests are.
- A new module, page or feature that is not already in the sidebar or the API. Two modules were once built without a brief and later had to be removed.
- Sign-in, roles, Keycloak, secrets and env files.
- `git push`, force-push, rebase, deleting or renaming a branch.
- Scripts that change or delete rows in a database, and anything to do with deployment.
- A new dependency.

**Not a zone, no check needed:** fixing a bug; wording, layout and styling inside an existing page; tests; a field added to an existing form in the pattern of the fields around it; reading and explaining code.

If a `CLAUDE.local.md` next to this file says you are working with Kimleng, skip this check and follow that file instead.

## Settled decisions (do not reverse without Kimleng)
- Tags and categories are flat lists owned by a tourism region: no children, no values.
- `is_featured` is gone from destinations, stays, foods and corridors (`v2/900-featured-retired.yaml`). Requests that still send it are ignored. `GET /api/v1/popular` ranks by browses first (distinct signed-in visitors, 30 days) and, since 2026-10-14, fills the row up to `limit` with verified places, then the best rated, then the catalogue A to Z (`items[].reason`: MOST_BROWSED, VERIFIED, TOP_RATED, CATALOGUE); `?type=` picks the kind (DESTINATION, STAY, FOOD, CORRIDOR) and `browse_events` carries `target_type` + `target_id` (`engagement/005-browse-target`). `GET /api/v1/recommendations/for-you` has no consumer and stays as it is.
- A verification decision carries a `basis`: OFFICIAL_SITE, PARTNER or PAID. PARTNER is refused unless the place's desk is PARTNER. The Traveler seal is computed on read from review summaries against `app.verification.traveler-seal.min-ratings` (10,000) and `min-average` (4.5), env `TRAVELER_SEAL_MIN_RATINGS` and `TRAVELER_SEAL_MIN_AVERAGE`. The public `GET /api/v1/destination-verifications/status` returns `verified`, `basis`, `travelerRecommended`, `ratingCount` and `averageRating`. Revoking a seal-only place answers 409.
- The `history` schema (History & Heritage) and the dish `section` column are dropped. Menus are not written any more. Decided again on 2026-10-16: History & Heritage does not come back, even though the developer's `visal` branch still carries it; features from that branch are ported without it.
- Amenities are one managed list with levels; the app reads `GET /api/v1/amenities` for labels and icons.
- `GET /api/v1/admin/destination-stats` (with `?from=&to=` as Cambodia dates) is the read behind the dashboard's Destination Stats.
- Reviews carry `visitType` (BUSINESS, COUPLES, FAMILY, FRIENDS, SOLO) and `visitedOn` (`YYYY-MM`, never in the future); `ReviewTargetType` and `RatingTargetType` cover DESTINATION, FOOD, STAY and CORRIDOR; `FavoriteTarget` includes CORRIDOR, REGION and PROVINCE. `GET /api/v1/reviews` and `/reviews/me` take `rating=` (1–5, repeatable): the author's stars on the same place.
- Tourism regions have `cover_key` (upload folder `region`); `RegionResponse` carries `coverUrl`. Since 2026-10-14 provinces have `cover_key` (folder `province`) and a centre (`latitude`, `longitude`; the 25 seeded capitals in `taxonomy/021`), regions a centre too; both answer `bounds` around their published places, a region's centre falling back to the middle of them (`centreSet` says which), and a province answers `placeCount`, `averageRating`, `reviewCount`. Internal callers read `ProvinceService.findSummaries()`, not `getAll()`.
- Since 2026-10-16 (ported from the developer's `visal` branch): interests have `cover_key` (folder `interest`, `taxonomy/022`; `iconKey` stays for the app), regions have `map_key` (`taxonomy/024`: ONE picture in the app's Map panel, where the interactive map of the region's places used to be) and `ams_recommended` (`taxonomy/023`, the Recommended by AMS Travel badge); a destination's `theme` may be any tourism region's code (`RegionService.isTourismCode`), so the OpenAPI schema publishes no theme enum; `GET /search?near=` takes `radiusKm` (0.1 to 50, default 25) and attraction cards found that way carry `distanceMeters` (`DestinationRepository.findNearbyDistances`, PostGIS).
- `PUT /api/v1/staff/{id}` (USER_MANAGE; 2026-10-16, for the dashboard's account form) edits a staff account's first and last name, e-mail and enabled flag in Keycloak, then mirrors name and e-mail and stores phone and photo on the person's row here (`UserService.mirrorStaffProfile`, making the row when the account never signed in). `StaffResponse` carries `phone`, `avatarKey`, `avatarUrl`. Disabling your own account answers 403. Roles stay on `PUT /staff/{id}/roles`, the password is Keycloak's.
- The app searches on the SERVER through the table-less `search` service: `GET /api/v1/search` (type, q, regionId/regionIds, provinceId/provinceIds, categoryIds, tagIds, interestIds, `travelerRecommended=true`, `near=` a destination for nearest-first; paged, name order, size ≤ 100), `GET /api/v1/search/by-province?perProvince=` (grouped), `GET /api/v1/search/suggest?q=`, `GET /api/v1/search/cards?type=&ids=`. A region id is a zone (through the province) or a tourism region (the shelf; corridors through their stops). Destinations run as a JPA Specification (the seal filter is two subqueries on `ratings`); stays, foods and corridors are filtered from their published lists. The card carries `openNow`/`todayHours` (food) and `stopNames`/`encodedPolyline` (corridors). `GET /api/v1/popular` also takes `provinceIds`, `regionIds` and `interestIds`.
- Stays are PRICE PREVIEW only. `destination_stays.weekend_nights` (JSON, default Friday and Saturday) and `destination_stay_rooms.weekend_price`; `GET /api/v1/stay-rooms/quote?stayId=&checkIn=&checkOut=&rooms=&adults=&children=` and `GET /api/v1/stay-rooms/{id}/quote` sum the nights (`RoomQuote`); the app shows one total, never a nightly price. There is no booking.
- Corridors have a gallery (`MediaType.CORRIDOR.hasGallery()`, `GET /api/v1/media?ownerType=CORRIDOR`); a photo made cover sets the corridor's cover. Food `openingHours` keys are `mon`…`sun`, values `HH:mm-HH:mm` or `closed`; `OpeningHours` reads them in Asia/Phnom_Penh for `openNow` and `todayHours`.
- A traveller has `home_province_id` (`auth/008`), `GET /users/me` answers `homeProvinceName` and `profileCompletion` (name, email, phone, picture, home province: 20 each; `ProfileCompletion`); `PUT /users/me` sends the whole profile, so a field left out is cleared. Preferences have `distance_unit` KM|MI (`auth/009`). `GET /badges/me/progress` answers `percentile` (rank among the season's active members by badges earned, then progress); an earned badge has `shareUrl` = `app.badges.share.public-url` (env `API_PUBLIC_URL`) + `/api/v1/badges/shared/{id}/page`, a public HTML page with Open Graph tags.
- Parked on 2026-10-14 by Kimleng (asked by the mobile team, not built): prices in riel, saved folders, helpful votes, reporting a review. Declined: a first/last name split. Khmer content was unparked on 2026-10-21 (next bullet).
- Khmer content (2026-10-21, ported from the developer's `visal` branch without the heritage pieces): attractions, stays and food places carry `nameKm`, `descriptionKm`, `sloganKm`, `sloganByKm`, `addressKm` (`destination/030`, `031`); regions and interests `nameKm` + `descriptionKm`, provinces, categories and tags `nameKm` (`taxonomy/025`); the seeded rows' Khmer is in `destination/032`–`033` and `taxonomy/026`–`027` (the developer's, attractions and the taxonomy) and `destination/034` (the 20 stays and 25 food places, written in-house on 2026-10-21; stays are matched by name, having no slug), and in the seed JSON for a fresh seed. Typed by hand, never machine-translated. On a request null keeps what is stored and blank clears it. Every listing response carries `missingKhmer`: the filled English fields with no Khmer yet, which the dashboard marks. Khmer is OPTIONAL for now: publishing does not wait on it (the developer's 409 `KhmerTextMissingException` was left out on purpose; a gate would go into the three listing services' publish paths and `PublishingServiceImpl.approve`). The app asks `?lang=km` on `GET /search`, `/search/by-province`, `/search/suggest` and `/search/cards`: cards and suggestions then carry the Khmer where written and name what is still English in `untranslated` (`SearchMapper.inKhmer`, `KhmerText`, `KhmerNames`); any search also matches `nameKm` and `addressKm`.
- The staging catalogue seed (2026-10-14) ships 60 attractions with long descriptions and galleries, 25 province covers and centres, region covers, corridor galleries, 20 sample stays with rooms, 25 sample food places, 24 sample travellers (`@seed.ams.test`, no sign-in) with their reviews, ratings and browses, and 12 Verified decisions. Stays, food places, travellers and reviews are FICTIONAL staging content; photos come from Wikimedia Commons with the credit in each gallery caption (`docs/SEED-PHOTOS.md`). One seeder per service under its `config/` (order TERMS…ENGAGEMENT), one `galleries.json` for every kind of owner. `app.seed.reset-token` (env `SEED_RESET_TOKEN`): a token never recorded in `system.seed_runs` wipes everything the seed wrote (reverse order, `wipe()`) and seeds afresh; staff edits to seeded rows go with it, so never set it on a server whose content is real. Since 2026-10-16 every interest has a picture (`interests.json` `image`, one of the catalogue's own photographs), every tourism region a map picture (`map-<code>.jpg`: its places on OpenStreetMap's standard tiles, rendered by `../local/seed-photos/region_maps.mjs`, credited in `photos.json` and `docs/SEED-PHOTOS.md`) and three regions the AMS Travel badge (`amsRecommended`); a server shows them after a NEW `SEED_RESET_TOKEN`.
- Activities & Experiences (2026-10-21, Kimleng's fourth kind of destination, the boss's mind map): `destination.destination_activities` (`destination/035`), `services/destination/activity`, `GET|POST|PUT|DELETE /api/v1/activities` with `?near=`, `?destinationId=`, `?slug=` like a food place. An activity is written like an attraction (province required, slogan, Khmer twins, cover from its gallery) but, like a stay or a food place, is classed by its interests alone: NO tourism region, category or tag. It has a `type` of its own (`ActivityType`: DIVING, KAYAK, BIRD_SANCTUARY, WILDLIFE, HIKING_TREKKING, FISHING, CAMPING, VIEWPOINT, CRUISE, SHOPPING, OTHER; the ten are the "Activities & Experiences" interest group) and the contact six (`phone`, `contactEmail`, `website`, `telegram`, `whatsapp`, `facebookUrl`). It belongs to a partner account like a stay (`ownerUserId`; same grants as `/foods`). `ACTIVITY` is a value of every kind list: search (`?type=ACTIVITY`, cards, suggestions, by-province; a region filter reaches it through its province's zone, as a stay), popular/browses, reviews and ratings, favorites, stamps, media galleries (folder `activity`), publishing requests, verification, Destination Stats. No price, no duration, no hours for now. The seed ships 5 (`activities.json`, with Khmer, reviews and browses; galleries reuse catalogue photographs); a server shows them after a NEW `SEED_RESET_TOKEN`.
- Check-ins (`POST /api/v1/stamps`, since 2026-10-20 the QR code posted on site AND the device position, one stamp per place per season, attractions, stays, food places and activities alike; the CMS issues and prints each place's codes through `/api/v1/stamps/codes`) are in scope. Since 2026-10-21 a place holds any number of active codes at once (`engagement/007`), each with an optional `label` saying where the print went; issuing never replaces, a code dies only through `POST /stamps/codes/{id}/retire` (`retiredAt`/`retiredBy`; retiring twice is a no-op), and `DELETE /stamps/codes/{id}` answers 409 once the code has check-ins. A stamp records `code_id`, so `GET /stamps/codes` answers `checkIns` per code (plus `issuedByName`/`retiredByName`), active first. The scanned code alone names the place a check-in lands on. Three badge ladders: Browser, Reviewer, Adventure; the Explorer (points) ladder was retired on 2026-10-20 and points stay as a season total only.
- Verified (since 2026-10-20) applies to attractions, stays, food places and activities alike: the four bases, the Traveler seal from reviews, the desk by the author (a stay's or a food place's partner). A decision carries `targetType`; `destinationId` on `/api/v1/destination-verifications` is the id of a place of any kind, with no key to the attractions table. Apple sign-in is out; Google may come as a Keycloak identity provider. The OTP sign-in is the email-code authenticator the Dockerfile builds from `src/main/keycloak`, which is not in the repo yet.

## Where things are
- `deploy/`: the Docker Compose stack (Postgres, Keycloak with the realm files in `deploy/keycloak/realms`, MinIO, Mailpit, the API, optionally the dashboard). The realm files carry placeholders that `deploy/keycloak/entrypoint.sh` (compose) or `local/run-keycloak.sh` (Kimleng's Mac) fill from the environment.
- `src/main/keycloak/`: the Keycloak email-code step (`ams-email-code`), compiled into the Keycloak image by the Dockerfile; `src/main/resources/login/` is the login theme.
- `docs/mobile/`: what the mobile team reads: the integration guide for the hosted API (nothing local in there; running the stack on a machine is `deploy/README.md`), the screen-by-screen endpoint map, the Insomnia/Postman collection, the Claude Code prompt, and `API-REQUESTS.md`, the gap-report template the app repo copies: the app never patches around a missing field or endpoint, it writes an entry there, and Kimleng brings the file to whoever changes the API. Keep `screens-to-api.md` and `postman/build-collection.py` in step with API changes.

## Schema rules
- Hibernate runs with `ddl-auto: validate`: an entity and its table must match or the app refuses to start.
- A schema change is a NEW changelog file under `src/main/resources/db/changelog/v2/<area>/` plus one `include` line in `db.changelog-master.yaml`. Never edit a changelog that has already run.
- Spring drops unknown JSON fields silently: a DTO field missing from a request arrives as null, with no error for the caller.

## How to work
- `./gradlew test --no-daemon` runs the suite on H2 in memory: about 25 seconds, 260 tests. A ten-minute run is Gradle contention, not the suite.
- Reseeding a local or staging database: `SEED_RESET_TOKEN=<new token> ./run-api.sh --bg` (from `../local`), or the same variable in Dokploy, then one restart. `CatalogSeedTests` seeds the whole catalogue on its own H2 database and checks every file's rows arrive; the content files are regenerated by `../local/seed-content/integrate.py` from the written content and `../local/seed-photos/photos.json`.
- `src/test/java/ams/asmtravel/api/support/` (Callers, TestCatalogue, ReferenceRows) was reconstructed from the tests that use it; keep it working.
- Code is grouped by service: `src/main/java/ams/asmtravel/api/services/<area>/<service>/{controller,domain,mapper,service,config,exception}`.
- The API's runtime env is not in this repo. On Kimleng's machine it is `../local/api.env`, and the stack starts with `../local/start-all.sh --build`.
- Commit when asked, one commit per repo, a subject in plain words and a body that lists what changed. Never push without Kimleng's go.
